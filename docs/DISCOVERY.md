# 动态核验与反例驱动修复

这条实验路径解决预设检查覆盖面有限的问题：模型根据当前问题编写参考计算、设计数据，再通过实际执行检查候选 SQL。它不需要开发者为每种业务错误增加一个 `property_id`。

这是受限数据分析原型，不是通用 SQL 正确性证明器。表结构仍是 `orders` / `order_lines`；复杂业务知识需要调用方在原始问题或 `definitions` 中提供。

## 一次任务的过程

1. **独立规划**：核验角色只接收原始问题、字段说明和数据约束，尚未看到候选 SQL。它生成参考计算、原文依据、未确认假设和小型测试数据。
2. **保存参考版本**：程序检查语法、字段、外键和资源限制。无效计划最多反馈修正三次，仍不暴露候选 SQL。有效计划成为不可原地修改的版本；未确认的业务假设转入澄清。
3. **生成 SQL**：生成角色独立读取原始任务。它没有参考程序或评分答案。
4. **执行检查**：只读内存 SQLite 执行 SQL，受限解释器执行参考计算。生成数据和绑定源数据均检查，保存实际结果、预期结果、程序摘要。
5. **盲态独立核算**：第三个客户端只接收原始需求和无答案的数据样本，不接收候选 SQL、原参考程序、任何预期值或生成方解释。它重新推导计算，工具执行中间变量和算术。此步骤也检查原先结果一致的任务，避免只调查显性冲突。
6. **寻找区分性数据**：Hypothesis 在当前表结构的合法数据空间内搜索三种计算不同的输入，并尝试缩减。它利用程序中的常量选择候选值，不按业务错误类别选择模板；搜索有样本与时间上限，没有找到反例不代表等价。
7. **分歧归因**：新的归因上下文查看原需求、两个参考程序、SQL 和执行证据，判断候选问题、参考问题或尚不确定。请求必须引用实际分歧的 `check_id` 和需求原文；程序重新检查支持方是否在全部保留数据上一致，并检查可选的调用方确认样例。普通 `repair` 请求不能直接修改 SQL。
8. **定向修改**：获准修改 SQL 后才调用生成方；获准修改参考时，将盲态独立核算提升为新版本，保留原版本、归因依据和全部旧反例，SQL 保持不变。默认最多替换一次参考。证据不足时澄清，不删除失败用例以获得通过。
9. **最终重放**：完成或恢复时重新执行当前 SQL、参考、独立核算、所有保留数据、源数据和调用方确认样例。旧任务适配还必须通过原有硬门槛。

三个角色可使用同一 Qwen 模型，但必须使用不同客户端与消息上下文，付费调用共用同一预算。核验角色的规划、归因和常规复核也各自构建上下文。这减少部分信息诱导，不意味着模型错误统计独立。归因会看到双方程序；盲态独立核算不会。

参考替换后，当前参考就是原先的盲态独立计划，两者不再是两份独立实现。后续重放用于检查新参考与候选在所有保留数据上的行为，不能解释成两个参考再次独立证明彼此。

## 修改权限与业务依据

执行差异只证明程序不一致，不证明哪一方符合用户意图。自动修改需要可执行证据与对原始需求的归因；匹配原文只证明出处，不能机器证明推理正确。没有外部确认时，授权标为 `model_supported_not_proven`。

调用方可另行提供 `confirmed_examples`：每项包含 `name`、合法 `data`、已确认的 `expected` 行和 `source`。这条输入路径独立于模型响应；模型不能通过声称“已确认”创建强依据。它可以来自人工核算或已审核业务定义，但 `source` 字符串本身不构成认证，调用方必须保证输入可信。

确认样例的预期不进入生成与盲态核算上下文；归因阶段可查看工具已经执行的确认结果。支持修改的一方若与任一确认样例冲突，授权被阻止。三种计算同时答错时，确认样例可以拦截；没有这类依据时仍可能共同误判。

不能将精度、单位、过滤条件或分母中的模型猜测当作业务要求。计划和审查提示要求说明依据，未知口径转入澄清；当前没有宣称自动验证自然语言的逻辑蕴含。整数结果精确比较，浮点仅保留 `1e-9` 绝对容差，避免大金额的相对容差吞掉整单位差异。

## 检查逻辑为什么不再写死

参考计算可组合筛选、关联、集合、汇总和算术，例如先构造符合条件的明细集合，再计算订单粒度的汇总。开发者实现的是通用计算操作，不是“订单均值错了”或“忘记换单位”的专用检查器。

参考程序是小型受限语言，外观接近 Python：允许局部变量赋值、推导式、下标、比较、条件表达式和固定的纯计算函数，最后一行返回结果行列表。没有 `eval` / `exec`，不允许导入、属性访问、函数定义、数据修改或文件/网络操作。解释器共享操作预算，限制数值、集合大小和程序复杂度。

支持列表、集合、字典和生成器推导式，字典同样共享执行预算且最多 1000 项，不开放 `dict.items()` 等属性调用。`round` 保留 Python 半偶规则；`round_half_up(value, digits)` 使用十进制 HALF_UP、精度限制为 0–9。它明确末步舍入语义，但不会把此前的浮点运算变成精确有理数运算。

计划格式不合法时，反馈包含通用 AST 诊断，指出不支持的语句和属性调用的位置，重申保留名称等约束，并给出与业务无关的语法示例。模型据此修正表达方式；该反馈不提供参考答案，不把受限语言扩展为任意 Python。

SQLite 路径允许聚合、去重、连接和分组子查询；禁止写入、外部数据库、任意函数、WITH、窗口和 UNION。数据库只包含本次提供的数据，并限制执行步数、时长和返回大小。这些是进程内的能力限制，不是操作系统级容器隔离。

## 原有核验如何保留

原 `tools/run_graph.py`、`ProbeGuard` 和六类性质检查未改动，继续使用原验收条件。

动态库入口为 `dataverify.agent.discovery_graph.run_discovery`，CLI 使用 `tools/evaluate_discovery.py`。适配原任务时可通过 `DiscoveryTask.legacy_task` 绑定原契约，此时旧核验仍为硬门槛。新增均值、去重、单位换算等任务超出了原契约，必须使用明确的探索模式，不能一边放宽旧契约，一边声称“击败相同条件下的强静态基线”。

旧检查会放行开发样例中的漏渠道筛选和漏单位换算 SQL；但它也不能接受这些新任务的部分正确 SQL。这反映原契约表达能力不足，不能直接换算成新旧系统准确率差异。

## 结果含义

- `reviewed`：保留测试与源数据均执行匹配，核验角色完成了有范围的审查。**不是语义正确性证明**。
- `needs_clarification`：业务口径不明确，或核验方认为测试预期可能有问题。
- `inconclusive`：程序、调用、执行或轮次约束使流程未完成。
- `unresolved`：已观察到分歧，但修复次数耗尽。

引用原文只证明依据可追溯，不证明解释正确。测试失败首先表示候选与模型提出的预期不一致，不能直接认定 SQL 错误。新测试不会自动成为永久的业务规则。

目前请求动作使用结构化 JSON，由本地调度器分发；没有声称使用模型供应商原生的 Function Calling 协议。

## 运行

与预设性质路径共用 LangGraph 环境。以下命令使用已安装依赖的 Python，见 [使用指南](USAGE.md)。

```powershell
python tools/evaluate_discovery.py --track controlled
python tools/evaluate_discovery.py --track correct
python tools/evaluate_reference_audit.py
```

以上命令完全离线，使用人工编写的模型响应，不衡量模型能力。第三项保留共同误解且无确认样例的失败场景，不把它算作正确结果。运行报告默认保存到新目录，避免覆盖历史实验。

真实模型需要已有普通千问 API 环境配置和累计预算账本：

```powershell
python tools/evaluate_discovery.py --live --track controlled --cases order_average --budget-file artifacts/current-budget.json
python tools/evaluate_discovery.py --live --track correct --cases web_scope --budget-file artifacts/current-budget.json
python tools/evaluate_discovery.py --live --track natural --cases distinct_orders --budget-file artifacts/current-budget.json
```

新实验续接账本使用 `--prior-journal` 和新的 `--budget-file`。所有角色共用一份账本，不重置累计消费；不要从旧账本分叉出多个可并发消费的分支。显式扩大技术请求次数或 token 停止阈值不会扩大累计费用上限。完整计费的截断响应可用 `--recover-truncation <原报告>` 续接；未知用量、传输异常不能走此恢复路径。

仅新账本续接可设置 `--input-char-stop`（最高 200 万累计字符）和 `--token-stop`；不能低于已用量，历史记录及金额上限保持不变。受控参考错误的真实实验可用 `--live --audit-scenario wrong_reference_rounding wrong_sql_grain requested_rounding`，配合上述预算参数。初始 SQL 和首版参考为公开注入，后续独立核算、归因、修复与复核才是模型实际行为，不能称作全自然生成。

实际调用仍保留 900 Token 单次输出上限。参考程序采用局部变量、较小初始数据和后续探查；无法在预算内完成时返回未完成状态。预算按公开标价保守预留，不等于云控制台实际扣费。

输入任意符合当前表结构的新任务，不必修改用例列表：

```powershell
python tools/evaluate_discovery.py --live --track natural --input tests/fixtures/discovery/custom_task.json --budget-file artifacts/current-budget.json
```

输入文件包含 `task`（`task_id`、`question`、`definitions`，可选 `legacy_task`）和 `source`，可选顶层 `confirmed_examples`。数据可采用 `orders` / `order_lines` 字典行，或兼容的 `orders` / `lines` 数组行。模型生成的新测试每张表最多 50 行，最多累计 12 组测试；当前比较保留重复行但忽略行序，不支持依赖排序语义的任务。

库入口 `run_discovery` 必须提供独立的 `auditor=` 客户端，支持 `pause_after="plan" | "execute" | "audit" | "attribute" | "replace_reference" | "repair_feedback"` 和 `resume=True`。检查点绑定原始任务、源数据、确认样例摘要、代码版本、角色配置和预算；内容变化时拒绝复用。模型调用前先提交 pending 标记，遇到中断后结果未知的调用，恢复时拒绝自动重发。新版本不会静默续跑旧版本检查点。

## v1.0.0 联调

移除 DB-GPT 后，使用同一累计预算进行真实千问联调。初次错误参考任务产生不支持的 DSL 语法，3 次请求后未完成；保留该运行记录，完善通用 AST 诊断后补测。

补测的 `wrong_reference_rounding`、`wrong_sql_grain`、`requested_rounding` 分别使用 6、6、5 次请求，完成正确 SQL 保留并替换参考、错误 SQL 修复、明确舍入保留。运行后用七组开发评分数据检查 SQL、当前参考和独立核算，三种计算均通过。这些场景受控注入首条 SQL 和参考计划，后续独立核算、归因和复核使用真实模型。

`distinct_orders` 自然任务的 SQL、参考与独立核算均由模型生成，5 次请求后返回 `[[3]]`，三种计算均通过七组开发评分数据。固定性质路径另完成 `d03` 自然生成和跨进程恢复：生成 1 次请求，恢复 0 次。

全部运行合计 26 次请求、53,194 Token，包含首次失败与后续补测；本地原标价估算增量 0.0610118 元，完整 usage 与脱敏轨迹见 [本版联调证据](../tests/fixtures/discovery/v1_live_validation.json)。这验证主要执行分支，没有形成独立留出评测，不能表述为一次测试全部成功，也不能把 API 联通等同于模型普遍正确。

## 参考审查改造的实测与局限

以下是移除 DB-GPT 前的参考审查开发记录：25 次真实 HTTP 调用、49,331 Token，按原账本标价估算增量约 0.0593 元；当时累计估算约 0.3979 元，累计费用上限为 5 元。费用是本地用量估算，不是云控制台扣费核对。

最终选定的三条开发轨迹分别完成：

- **错误参考**：保留正确 SQL，将擅自舍入的参考替换一次，保留旧版本与反例。
- **错误 SQL**：保留参考，调用生成方修复订单均值粒度。
- **明确舍入要求**：保留正确 SQL 与符合要求的参考，没有一律禁止舍入。

运行结束后同时评分最终 SQL、当前参考程序和独立核算，不只检查 SQL。三条最终轨迹均通过七组开发数据：源数据、订单粒度、空数据、循环小数、半值舍入、退款和混合边界。评价答案及这些额外数据没有用于当次模型输入；但数据参与了迭代分析，不能称作独立留出集，也不能推导生产准确率。

所有失败均保留：首轮错误参考场景因引文概述/语法问题中止；早期明确舍入场景在原输入通过，却在 `0.125` 半值上暴露 SQL `0.13`、两个 Python `round` 参考 `0.12` 的差异；引入语义明确的 `round_half_up` 后，一次调用又因不支持字典推导式中止，随后在有限语言中支持该语法并通过补测。最终成功不是一次固定版本评测的 100% 成功率。

[公开证据包](../tests/fixtures/discovery/reference_audit_evidence.json) 包含六条实际运行记录、成功与失败、参考版本、执行轨迹及三方追加评分；不包含密钥、完整私人请求上下文或消费账本。九类离线矩阵另明确展示共同误解且无确认样例时仍可能错误放行，有确认样例时阻止发布并澄清。新流程降低部分误改风险，尚未证明整体准确率的提升。

移除 DB-GPT 前，该次开发版本完整回归 930 项通过、12 项可选集成跳过，代码与格式检查通过；这是历史版本的测试口径，不是当前候选版的通过数。真实归因轨迹仍可通过 `tests/test_discovery_evidence.py` 离线重放。

## 历史实验及局限（参考审查改造前）

更早的动态核验增量实验共 67 次真实 HTTP 调用、94,185 Token，按已记录公开标价估算约 0.1144 元。包含失败、语法修正和重复实验；累计费用账本未重置。这不是云账单核对结果。

最终开发轨迹包括：

- 四类受控首条错误的成功修复：订单均值粒度、渠道筛选、订单去重、金额单位。初始错误由测试注入，参考程序、测试数据和后续修改均由千问生成。
- 两条正确候选保留：订单均值、渠道筛选，均未触发 SQL 重写。
- 两条自然生成任务：订单去重，以及未登记在四个开发用例中的“web 渠道正净额订单合计”。后者通过 `--input` 输入，模型完成组合条件和先汇总后筛选，最终结果为80，与人工按源数据核算一致。
- 一次错误预期注入：正确 SQL 返回 `10.333…`，故意给出的参考预期为 `10.33`。真实裁决返回澄清，没有要求 SQL 迁就未经确认的四舍五入。

七条成功轨迹的最终 SQL 均在五个评分数据实例上与评测侧参考 SQL 一致，包含空数据、精度、时间边界、状态及不同渠道。评分用参考 SQL 不进入模型上下文。评分数据与本项目同时设计，仍是开发验证，不能称作独立留出评测或生产准确率。

后续审查发现，两条均值成功轨迹的模型参考计算仍带有未要求的 `round(...,2)`。在订单金额 `10、10、11` 上，原核验层对正确 SQL 的 `10.333…` 报分歧，却接受舍入后的 `10.33`。上述五数据评分只验证最终 SQL，没有验证参考程序泛化。新归因流程以此作为实际缺陷来源，历史证据不覆盖或改写。

必须同时保留失败记录：早期模型复制说明性占位文字、产生非法表达式/数据；一次生成的参考计算自行加入两位小数，并诱导生成方误改 SQL。后续将裁决上下文与参考程序隔离。`final_controlled` 首轮为 3/4 完成，单位换算因追加测试外键非法停止；完善工具错误反馈后，补充运行完成单位换算。不能把迭代后的成功样例合称为一次冻结评测的 100% 成功率。

公开的 [脱敏开发证据](../tests/fixtures/discovery/live_evidence.json) 包含成功轨迹、早期失败索引、评分结果及错误预期挑战。离线测试可重放成功轨迹中的动态检查。模型仍可能共同误解业务意图；缺少业务口径时不能自动创造事实。后续需要未参与调试的任务、更多正确 SQL 变体及独立人工标注，检验真正的新增检出率和误报率。

改造前交付目录回归结果：832 项通过、12 项因未安装可选 DB-GPT 运行环境跳过。这个数字表示当时的工程测试结果，不表示真实任务数量或参考计算的正确率。

## 源码入口

- `dataverify/agent/discovery_graph.py`：上下文、调查/修复路由、检查点与最终重放。
- `dataverify/agent/discovery_audit.py`：盲态独立核算、分歧归因和参考版本替换。
- `dataverify/agent/discovery_model.py`：核验动作协议和角色提示词，复用既有 HTTP 计费客户端。
- `dataverify/verification/discovery_runtime.py`：任务与数据校验、SQL 执行及预期对照。
- `dataverify/verification/reference_expression.py`：受限参考计算解释器。
- `dataverify/verification/reference_audit.py`：三方执行证据、确认样例硬门槛和区分数据搜索。
- `dataverify/evaluation/discovery_cases.py`：公开开发用例及评测答案，只在评测侧使用。
- `dataverify/runtime/discovery_budget.py`：仅对用量完整的截断响应进行显式续账审查。

## 方法参考

[TS-SQL](https://aclanthology.org/2025.findings-emnlp.156/)讨论生成测试数据和测试代码，以执行反馈改进 Text-to-SQL。本项目参考其方法方向，没有复现论文完整系统或其指标。

[Argus](https://github.com/joyemang33/Argus)将模型提出的新等价测试模式交给形式化工具验证，面向数据库引擎测试。本项目没有接入其等价求解器，也没有把自然语言口径视为可由 SQL 等价性证明。
