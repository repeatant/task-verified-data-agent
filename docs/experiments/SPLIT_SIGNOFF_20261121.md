# SQL 核验的签核依据与辅助说明

同一条模型回复有两种用途。当前版本的执行回放支持交付，针对原库的只读查询可以解释判断。旧协议把两类 ID 都装进 `evidence_ids`，要求每个 ID 都来自当前回放。新协议把两者分别写入 `signoff_ids` 和 `supporting_ids`。后者允许为空。签核仍须有当前回放证据，所有保留样本都须通过，业务假设必须解决，交付 SQL 最后在绑定的数据源上实际执行。

## 相同状态的真实千问对照

先在上一轮九条末轮限定轨迹中选出全部四条因混引而未交付的末步。用执行记录重建前三轮的原始提示、模型动作、修订后的三个程序、回放、调查结果和动作预算。新旧两组在同一状态各发一次新的千问请求，仅在分岔时改变签核契约。两组顺序交替。此前九条轨迹均已见过。纳入实验的四条是针对已知故障的回归样本。

四条的 SQL、参考和独立核算在隐藏评分数据及完整库上均正确。评分还核对 SQL 与实际交付数值是否一致。另在前两条状态上解除末轮动作限制，检查工作台常规模式。两个错误候选包含原要求未覆盖过的订单渠道和空渠道问题。不同组的轨迹单独统计。

| 组别 | 旧单列 | 新分栏 | 实测含义 |
| --- | --- | --- | --- |
| 四个曾被引用规则误拒的正确状态 | 正确交付 1/4，混引被拒 3/4 | 正确交付 4/4，混引被拒 0/4 | 新增三次正确交付；两个策略均未交付错误的 SQL、参考或数值 |
| 常规模式两个决策点 | 正确交付 2/2 | 正确交付 2/2 | 同一问题的新调用，未观察到额外增益 |
| 两个错误候选 | 错放 0/2 | 错放 0/2 | 四次模型回复均未通过格式校验；未运行到交付证据校验 |

回归轨迹 03 中，旧版把当前检查 ID 与调查查询 `q0002` 放在同一列表，交付被拒。新版各放到对应字段，数据库返回 669，与评分一致。轨迹 04 的旧版本调查 ID 在新签核时已经过期，这次新旧策略都仅引当前回放、交付 26。不能把历史上四次拒绝与今天新版的四次成功直接当成四次改善。此次比较的两边都是新请求，原记录只负责固定决策点。

首次负控的请求携带了能提示故障方向的内部任务 ID。另有四次真实请求使用匿名任务编号，详见下文。两组错误状态的强制合法签核均已另做离线检查。明显分歧时，新旧两种宿主都实际拒绝了签核。对于“三份程序同时把未知渠道也算成一种”的共同错误，预览只有 web 渠道，三方在预览上一致。给出格式正确、证据有效的 finish 时，**两种协议都放行了错误 SQL**。这类问题需要能区分两种含义的数据或来自用户的可信样例。引用分栏本身不会制造这份证据。[评分器与负控](../../dataverify/evaluation/signoff_controls.py) · [合法签核的边界测试](../../tests/test_signoff_controls.py)

主实验使用 `qwen3.8-flash`，新增 16 次成功 HTTP 请求，输入 25,922 tokens，输出 2,663 tokens，共 28,585。协议指纹为 `a4aec2738361eee626809ca4a4ed04034afe707218a852ed5cd4c5167f4047a3`。已冻结的两个程序版本使用同一客户端、数据库和原累计预算账本。真实调用只发生在决策点，重放前缀不产生模型请求。单次采样与定向选样限制了结论。常规流程未满足预登记的新增正确交付门槛，保留原默认策略。

## 匿名负控的真实压力检查

另外固定两个错误候选，各用新旧协议取一次样。在创建任务时用无语义哈希替换故障名称，逐轮检查完整提示，禁止传入内部故障标签。两组共用同一数据库、问题、前三方程序和调查结果，末轮均使用千问的严格 JSON Schema 模式，给出相同的中性要求，允许交付、澄清或明确弃答。四个决策全部格式合规。

- **可观察的分歧。** 只该统计门店订单，SQL 却计入了线上订单。实际回放为候选 1、参考 0。两次千问调用都指出缺失门店条件并选择弃答，均未交付。
- **三方共同出错。** 需求要求排除未知渠道，SQL 却先将 NULL 换为字符串再去重，两份参考也把 NULL 算作一种渠道。单行预览不含 NULL，三份程序的结果相同。两次千问调用都从需求和程序中识别出这个矛盾，主动弃答。在离线控制中强制发出证据有效的交付指令，新旧宿主则都会放行。这里的拦截来自模型做对了判断。

匿名组新增 4 次成功 HTTP 请求，共 5,638 tokens。首个只含预登记的目录 `reports/split-negative-v1` 在付款前因 JSON 序列化类型不一致退出，调用数为零。正式记录位于 `reports/split-negative-v2`，协议指纹 `f9ed507df5e7eb01befc6334feaf0883b3610b436aa0ada659351f6b9aa7b6ea`。重复抽样次数为零。此前主实验和这组压力检查合计新增 **20 次成功 HTTP 请求、34,223 tokens**，两边的请求及样本分别计数。[匿名压力检查脚本](../../tools/probe_signoff_negatives.py)

本机可在工作树根目录复核原始记录、每次模型收到的提示、真实调用事件摘要和最终评分。命令只读取已完成的任务，重新运行核验与评分。

主实验里分栏协议交付了六次，涵盖四个不同的正确状态。独立复核时，在相同的程序、数据和执行记录上，将每条已交付回复的 `signoff_ids` 原样放回旧协议的 `evidence_ids`，仅去掉辅助说明。旧签核逻辑六次均通过，交付 SQL、源库标识、回放标识和实际返回数值也逐条相同。这解释了本次新增交付的原因，同时保留了隐藏共错的反例。[复核测试](../../tests/test_signoff_controls.py)
