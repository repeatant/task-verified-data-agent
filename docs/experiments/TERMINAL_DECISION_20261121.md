# 为分歧处理保留最后一次决策机会

在四次模型动作的上限内，最后一次调查可能找到了线索，却没有机会让模型读取结果并作出决定。本实验保留前面三步的权限，将最后一次动作限定为交付、向用户澄清或因技术不确定而停止。交付仍须引用当前版本的执行证据，通过已有核验并在绑定数据库上成功执行。

## 配对结果

分母是问题轨迹。一个问题在多个评分数据集上的执行均计在同一条轨迹内。新场景由单独的评测贡献者为本轮编写，与开发集共享订单数据模型，未使用 BIRD 保留集。

| 数据与策略 | 正确交付 | 错误交付 | 未交付 | 进入第四轮 | 请求 | tokens |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 原六条开发轨迹，常规策略（历史对照） | 4/6 | 0 | 2 | 3/6 | 20 | 39,149 |
| 原六条开发轨迹，末轮限定 | 2/6 | 0 | 4 | 4/6 | 22 | 43,363 |
| 本轮三个新场景，常规策略 | 1/3 | 0 | 2 | 2/3 | 11 | 20,765 |
| 本轮三个新场景，末轮限定 | 0/3 | 0 | 3 | 3/3 | 12 | 22,252 |

开发轨迹 03 和 04 仅常规策略正确交付，02 和 05 两种策略均正确交付，01 和 06 均未交付。新场景 01 仅常规策略正确交付，其余两题均未交付。每一次实际交付的候选、参考与独立核算程序也都通过了相应评分集。

预先登记的默认启用门槛未达到。工作台继续沿用原有决策方式，额外调查仍由用户选择。保留末轮策略作为实验选项。

## 轨迹解释

- 开发轨迹 01、03、04 的末轮决策都尝试交付。每次模型都同时引用了当前重放证据及一条调查查询 ID。现有交付签核要求每个提交的 ID 都属于当前重放或其中的检查；混入调查 ID 后整个交付被拒绝。补充依据的引用方式本身影响了交付率，单独预留一次模型调用没有解决这一问题。
- 新场景 01 要求统计有待处理明细、且没有任何已结算明细的订单。两个策略拿到相同的初始程序。常规策略在第三步正确交付。末轮限定策略看到单行预览未覆盖混合状态，即使已有更完整的调查结果，仍选择弃答。新场景 02 的末轮交付引用未通过，03 的末轮返回不符合动作契约。没有把弃答记作正确回答。
- 九对运行的第一轮模型消息相同，后续各臂独立采样。同一问题两条轨迹都走到第四轮的，开发集共三对，新场景共两对；逐条对比这些运行的前三轮请求，没有一对三轮都相同。因此本表描述完整策略的实际表现，无法单独归因于最后一次提示。相同历史前缀的机制检查应另列分母。

## 固定前三步，只重做第四步

另取最初触发本次改动的开发轨迹 01。前两组端到端运行都允许模型从头选择动作。这次[单步对照](../../tools/probe_archived_final_turn.py)逐条比对原来的完整提示，重放首次格式错误、修订 SQL 和按状态查询这三个步骤。第四轮的任务、程序版本、查询结果和回放数据完全相同，只切换系统提示与剩余动作权限。

历史第四步又查了一次数据库，模型随后耗尽预算。新的第四步转为询问“退款是负金额，还是独立状态”。独立评分器在各份测试数据上确认当时的 SQL、参考程序及独立核算均正确，两条轨迹都没有交付。只给模型最后一次作决定的机会，可以阻止继续查询；这一例中，模型仍无法从已有证据判断是否有必要问用户。该结果只针对这一个固定状态。

单步对照新增 1 次成功 HTTP 请求，输入 1,510、输出 99，共 1,609 tokens。前三轮和旧第四步采用历史记录。与主实验合计，本轮新增 46 次请求、87,989 tokens。两项实验各自保留分母。本机可通过 `python tools/probe_archived_final_turn.py audit` 离线重放。

## 复核

[实验驱动](../../tools/evaluate_terminal_decision.py)在首次付款前冻结源码、原始程序、数据和评分指纹、已有六个对照文件的哈希、试验顺序与启用门槛。两臂同用千问、同一数据源、四次动作、两次调查及两次修订上限。开发集沿用原有 25 份评分数据，三个新场景各有七份数据，由分开编写的 Python 计算校验。新场景首臂按序交替。每格只执行一次。
