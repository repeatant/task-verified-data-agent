# 主动查询与正确交付（2026-11-21）

在六条受控开发轨迹上，简单 SQL 自审正确交付 6 条，允许主动查询的三方流程交付 4 条，修正动作提示后的无查询三方流程交付 5 条。此次开发结果不足以支持将主动调查作为默认修复策略。

## 实验设计

固定六条既有轨迹、五个原始需求和三个初始程序。每条轨迹的原始一行预览是统一合成数据源的前缀。数据生成器仅使用种子和预览，总共 17 张订单、120 条明细，不读取故障标签或预期结果。所有方法在同一数据源交付。诊断角色只能看到预览和保留的执行记录。模型可访问的数据不含手工挑选的区分样本。

简单自审读取初始 SQL 在完整数据源的执行结果，一次调用后交付。两个三方臂共享相同初始程序、提示基础、输出格式、单请求字符和 token 上限、四次模型动作与两次修订额度。原始配对只改变调查查询权限；各臂最终 SQL 都在完整数据源真实执行。评分器单独对 25 份数据检查最终 SQL（含原预览和 24 份独立评分数据）。审计还以手算口径复核每份实际交付中的数值。六条轨迹共享部分需求，25 次执行也属于同一条轨迹，不能增加独立需求的分母。

## 两轮实测

下列各行均为真实模型调用。第二协议复用了首轮的自审及开查询记录，只补跑了修正后的六条关查询轨迹。

| 方法 | 正确交付 | 错误交付 | 未交付 | 诊断查询 | 模型请求 | 总 tokens | 六条累计用时（秒） |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 简单自审 | 6 | 0 | 0 | 0 | 6 | 4,020 | 13.97 |
| 关查询（原协议） | 3 | 0 | 3 | 0 | 18 | 33,614 | 51.74 |
| 开查询（原协议） | 4 | 0 | 2 | 6 | 20 | 39,149 | 63.52 |
| 关查询（修正动作提示和校验） | 5 | 0 | 1 | 0 | 14 | 25,849 | 52.94 |

首轮开查询比关查询多交付两条、少交付一条。原关查询组的系统提示仍列出 query，虽然上下文已报告工具关闭。在第 03 和 05 条上，模型连续提出被禁用的查询，流程以无进展退出。这个实现细节会让开查询看似有利。

为检验这一解释，另冻结一个仅复测关查询组的协议。三个可选动作、剩余查询次数以及客户端动作校验均与实有权限一致。保持与原实验一致的 JSON object 传输格式。修正后第 03、05 条都正确交付。与原开查询组逐条比较，共四条均成功、一条均未交付，第 01 条只有修正的关查询组交付。第 01 条开查询轨迹先出现一次动作格式错误，再修正 SQL，随后两次查询用尽动作额度。把这两轮算成十二道新需求，或主张已证明查询具有负效应，都超出了样本。

四个实际运行臂均修正了最初出错的三个 SQL，均未观察到正确 SQL 被改错。剩余差异出现在能否交付；第 06 条的三份程序最初共同错误，而单轮诊断最多修订两份程序。该结果说明了协议的能力边界。留出题仍未启用。下一步优先改善任务的呈现、澄清、进展反馈和有条件退出，不据此扩大裁判角色或加入新的个案规则。

共 24 个实际运行单元，58 个独立 HTTP 计费事件，92,317 个输入 tokens，10,315 个输出 tokens，合计 102,632。事件的 usage 均完整。按项目冻结估价折合约 ¥0.102，最终计费以供应商账单为准。
