# v1 冻结评测方案

日期：2026-11-07。本文在本轮真实模型运行前制定，规定样本、评分、对照和失败处理，不包含预填实验结果。

## 要回答的问题

本轮检验 DataVerify 的动态核验与定向纠错能否处理四种情况：错误 SQL、错误参考、两者共同犯错，以及本来正确的计算。重点是结果是否正确交付、错误是否被放行，以及正确 SQL 是否被错误修复。

研究对象是当前 LangGraph 运行路径。运行期间不改变运行时代码、模型提示词或图路由，不修改旧实验与历史版本。本轮是公开开发案例上的受控挑战与自然生成检查，不是独立未见测试集、生产准确率评测或通用 Text-to-SQL 排行榜。

以下是待检验假设，不是预期必须获得的结果：

- 仅能执行、或与一份参考一致的 SQL，仍可能违反任务语义。
- 从原始需求重新生成的独立核算可能发现首版参考和 SQL 的共同错误。
- 依据执行分歧选择修改对象，有机会修正错误参考并保留正确 SQL。
- 额外核验也可能增加调用成本、格式错误和未解决任务；模型间一致仍可能伴随共同误解。

## 样本与运行次数

主评测使用四个已有业务意图：`order_average`、`web_scope`、`distinct_orders`、`money_units`，分别涉及订单级平均、渠道范围、订单去重和金额单位。

每个意图包含以下四种受控状态，共 16 条轨迹：

- `sql_wrong`：注入错误 SQL 与正确首版参考。
- `reference_wrong`：注入正确 SQL 与错误首版参考。
- `correlated_wrong`：注入犯同一种语义错误的 SQL 和首版参考。
- `correct`：注入正确 SQL 与正确首版参考。

另对每个意图运行一次 `natural`，不注入 SQL 或参考，共 4 条轨迹。计划总量为 20 条，受控组与自然组分别报告；每条仅运行一次，不根据结果挑选重跑版本。

受控组仅替换首个 SQL 和首版参考计划，不注入归因目标、独立核算、后续修复或结束决定。独立核算、归因及后续动作均调用真实模型。自然组的所有模型产物均由真实调用生成。

主集的原始数据可能已经暴露错误，这是当前设计的已知偏差：它检验模型如何核验与修复，但不能单独证明系统能从表面一致的数据中发现潜在错误。不得用本轮结论替代后续专门设计的隐蔽错误挑战。四类意图都来自已公开开发案例，不应声称业务问题对开发者完全未知。

## 冻结与信息边界

首次请求前保存机器可读 manifest，至少记录：

- 运行时代码提交及实际源码摘要；评测器、评分器与本方案摘要。
- 20 条任务的固定 ID、顺序、条件、原始需求、输入数据摘要及注入内容摘要。
- 所有评分数据、随机种子和独立标准计算实现的摘要。
- 模型标识、采样参数、响应长度限制、依赖版本和图运行上限。
- 预算账本来源、累计调用与费用起点、当前获准的累计上限。

沿用运行时默认的有限循环：最多 3 个候选尝试、3 次常规复核、1 次参考替换、每个程序组合最多 40 次反例搜索样本。真实客户端使用温度 0、最多 900 个输出 Token。温度 0 不意味着远端服务或整条轨迹必然确定；不得把单次运行解释为重复运行稳定性。

任何明确改变这些值的实验，都须先保存新 manifest，不能与本轮结果混为同一次冻结运行。运行后再次核验源码摘要；若运行时发生改变，则标记本轮协议偏离。

标准答案只属于评分器。模型上下文不得包含 gold SQL、独立标准计算、目标错误类型、预设归因目标、标准结果或评分数据。条件 ID 也不得作为提示告诉模型应修改谁。公开需求本身可以包含必须实现的业务约束。

本轮不提供用户确认的带答案样例，因此不把外部答案锚点的帮助混入独立核算结果。角色的原始请求与响应仅保存在私有运行记录中，公开投影移除密钥、端点、个人路径和服务请求标识。

## 标准结果与评分数据

每个业务意图使用独立普通 Python 计算作为评分标准，不调用运行时的参考 DSL，也不从待测 SQL 导出标准答案。评分实现须用可人工验算的小数据和正确 SQL 进行离线交叉检查；发生不一致时，先修正评测器并重新冻结，再开始真实运行。

每条轨迹评分使用 31 组固定数据：7 组显式案例和 24 组固定种子生成的数据。显式案例包括原始数据及空输入、统计粒度、精度、退款、时间和状态边界等适用情况；具体内容以冻结 manifest 为准。随机样本遵守主外键和字段约束。冻结后不依据模型失败增加或删除本轮评分数据。

运行时生成的反例与这些评分数据分开：前者可以影响修复，后者只在一次轨迹结束后离线评分。未决答案、未发布候选和参考程序也可用于诊断评分，但不能因此记为已正确交付。

最终 SQL、当前参考、独立核算参考均须在同一组数据上评分；首版参考另外保留评分，用于判断是否确实纠正了参考。任一输入上执行错误或结果不符，就不满足该计算物的“全部通过”。结果比较采用项目已有的明确数值容差与无序结果行契约，不通过单纯比较 SQL 文本判定语义正确性。

31 组数据是一个任务的多项检查，不是 31 个独立任务。报告不得把 20 条轨迹扩写为 620 个独立问题，也不得把同一意图下高度相关的注入状态解释为独立业务领域。

## 两个低成本对照

在完全相同的首轮 SQL、参考和输入上离线重放：

1. **静态合法性检查**：记录首轮 SQL 是否满足所用语法、只读和执行检查。必须在报告中列明实际运行的检查集合，不能把它命名为完备语义验证。
2. **单参考执行门禁**：只比较首轮 SQL 与首版参考在初始输入和首轮样例上的结果；格式错误、执行失败与结果分歧分别记录，不接触独立核算及其后来生成的样例。

这两个对照衡量初始产物会被哪些检查接受或拦下。完整 v1 的结果包含额外核算、反例、模型归因和修复，衡量的是后续实际交付。二者的工作量与能力范围不同。

因此只比较“哪些错误原本会被放行、完整流程后来如何处理”，不把门禁接受率与完整流程成功率相减后称为算法提升。没有真实运行无 auditor 的完整修复系统，本轮就不是 auditor 消融，也不能把观察到的变化单独归因于独立核算模块。

## 指标与分母

受控组分母为 16，自然组分母为 4；按错误条件细分时，每组分母为 4。记录分子与分母优先于只报百分比，不用这种规模推断总体准确率。

主要终态指标互斥报告：

- **正确交付**：状态允许发布，且发布 SQL 通过全部 31 组评分数据。
- **错误放行**：状态允许发布，但发布 SQL 在任一评分数据上出错。
- **未交付**：需要澄清、未解决、预算终止、格式失败、运行异常等未发布状态；继续按原因分类。拒绝一个错误答案不等于完成任务。

补充指标：

- **错误 SQL 修复**：在初始 SQL 经评分确实错误的受控任务中，最终正确交付的比例。主分母为 `sql_wrong` 与 `correlated_wrong` 共 8 条，另分别报告两组。
- **正确 SQL 保护**：初始 SQL 正确的 `correct` 与 `reference_wrong` 共 8 条中，最终 SQL 的语义仍正确的比例；是否已发布另外报告。未生成最终 SQL 的任务不计保护成功。
- **SQL 误改**：初始 SQL 正确、最终候选却错误的任务数。仅文本变化但结果保持正确不计误改；文本是否改变可以作为诊断字段。
- **错误参考纠正**：`reference_wrong` 与 `correlated_wrong` 共 8 条中，当前参考通过全部评分的比例；是否产生了新版本、最终是否发布均另记。
- **参考与核算质量**：当前参考、独立参考的全部通过数分别报告。它们正确也不能替代 SQL 的正确交付。
- **初始门禁错误放行／正确拦截**：以离线评分判定初始 SQL 真正正确或错误，再统计两个门禁的接受、拒绝与执行异常。缺少初始产物不能算门禁拒绝正确。

每个任务保留实际 HTTP 次数、重试次数、输入与输出 Token、端到端耗时和本地标价费用估算。汇总报告总量与每任务分布。不同错误条件通常触发不同调用数量，不把控制流差异当作同等工作量的性能优化。

## 失败、预算和协议偏离

预期可能出现 DSL 格式失败、引用不匹配、归因无法授权、共同误解、修复耗尽、评分不通过、超时或额度不足。这些均保留，不能只展示 reviewed 的轨迹。

有限流程内部已经允许的格式反馈和重试属于同一任务，全部计入调用与费用。整个任务结束后不重新启动以替换差结果。基础设施恢复只能延续同一已保存任务；可能已计费但结果未知的请求不自动重发。

本轮在用户批准的累计 8 元上限内执行：原 5 元账本完整保留，为本实验分配新增的 3 元额度，使用单独增量账本并记录父账本摘要、完整起点和授权额度。父账本旁保留分配记录，防止同一新增额度被重复分配；每份报告累加新旧账本的请求、Token、费用预留与估算，不把新账本解释为旧消费归零，也不释放旧保守预留。保守费用预留、本地 usage 标价估算与云端实际扣费分别说明；不能把预留当实际账单，也不能假设本地估算等于最终账单。

唯一允许解除已停止预算、继续后续任务的服务异常，是已完整核算的响应截断：HTTP 200、明确的输出长度截断、completion Token 等于既定 900 上限、usage 与逐请求账本及任务起止总量完全一致、无未知或在途请求，且本任务没有其他服务异常。复用现有的严格截断复核规则，保留原失败账本与续账关系；失败任务仍记失败，既不重新生成，也不提高输出上限，仅执行固定清单中下一条尚未开始的任务。此例外在首次运行前确定，不能因实验中某类失败较多而扩展。未知扣费、超时、其他服务错误或核算不一致仍终止后续付费请求。

若预算阻止剩余任务运行，保留完整 20 条计划清单并将未启动项标为未执行；同时报告已执行与全部计划分母，不用“只执行成功任务”改变分母。此时只能交付阶段结果，不能称整个实验完成。

发现运行时代码缺陷时，先保留本轮已发生的失败。修复后必须另开版本和协议，不能覆盖原记录后声称本轮一次完成。若发现评分器有缺陷，应公开说明原因、保留原评分及修订评分；评分修订不触发挑选性重跑模型。

## 产物与结论范围

最终产物包含冻结 manifest、20 条运行状态、私有原始轨迹、逐任务评分、对照结果、成本汇总和脱敏公开证据。报告与 README 只能填写实际得到的数值；简历指标必须能回指任务清单和计算口径。

允许得出的结论包括：在这 16 条受控任务与 4 条自然任务中，发现、修复、保留和交付各多少，以及额外花费多少。不能据此声称通用多 Agent 正确性证明、跨 schema 泛化、生产系统收益、模型统计独立，或真实模型发现了所有未知错误。
