# 分歧处理开发对照

真实实验：2026-11-07；接口修复收尾与离线回放：2026-11-09。
实验分支 `experiment/evidence-recovery`，基于 `51a544c`。
本次保留既有主流程和扩展评测，新增显式调用的分歧处理入口。
它已能修改独立核算程序，并保存修改依据和重放结果；尚无证据表明整体正确交付
优于简单自审，也没有替换默认流程或发布到 GitHub。

## 改动解决什么

旧流程没有直接修复独立核算程序的出口，容易把计算程序的错误当成业务需求不清楚。
新诊断环节拿到原任务、三份当前程序和同一批数据上的执行差异，可以：

1. 在主机绑定的数据源上执行受限只读查询，读取真实返回结果。
2. 指定修改 SQL、首参考或独立核算中的一份，引用需求与当前执行记录。
3. 在保留数据上重跑三份程序，保存旧版本、拒绝的修改及退出原因。

主机检查引用是否存在、版本是否匹配、程序是否可执行及整轮比较是否通过；
这些检查不能证明模型的需求解释正确。没有引入多数投票或不可质疑的“正确参考”。
代码和接口见[分歧处理说明](../DISPUTE_RECOVERY.md)。

## 冻结范围

- 六条受控故障轨迹，来自五个已见原始需求；不是六道新题，更不是公开题泛化评测。
- 分别覆盖 SQL 错、首参考错、独立核算错、SQL 与首参考共同错、全部正确、三方共同错。
- 各方法读取相同任务；旧三方和新三方得到相同初始程序及可见诊断样本。
  简单自审只产出 SQL，不要求生成或修复参考程序。
- 可见诊断样本由实验预先提供，包含重复金额、负金额及日期边界等记录。
  它不包含期望答案，但不是模型自主找到的样本。
- 最终每份程序在 25 组固定数据上独立评分；其中源样本可见，其余 24 组评分数据
  不进入模型上下文。单条任务的这些数据不是 25 个独立自然语言需求。
- 新流程最多四个模型动作、两次查询、两次修订；旧流程四次请求由各角色共享。
  简单自审仅一次请求。旧流程原有的生成式挑战仍保留，因此这是整套方法比较，
  不是已经控制所有因素的单模块消融。
- 新流程和简单自审的交付源为共享可见诊断样本，旧流程交付源为原源样本。
  评分分别核对各自交付来源，并在相同 25 组数据上检查最终程序语义。
  这项来源差异必须在下一轮配对实验消除。

## 首轮真实模型结果

以下分母均为六条轨迹；“正确交付”还要求实际输出来自声明的数据源且与执行结果一致。

- 简单自审：最终 SQL 正确 6/6，正确交付 6/6，错误交付 0/6；6 次请求。
- 旧三方流程：最终 SQL 正确 4/6，正确交付 3/6，错误交付 0/6；15 次请求。
- 新分歧处理：最终 SQL 正确 6/6，正确交付 4/6，错误交付 0/6；17 次请求。
  最终三份程序同时正确为 5/6；剩余一条的独立核算仍错。

新流程成功交付了旧流程未完成的两条任务：独立核算单错、SQL 与首参考共同错。
共同错案例中，模型先执行 `COUNT(*)` 查询，观察到六条符合条件的记录，再分别
去除 SQL 的 `COUNT(DISTINCT amount)` 和首参考的集合去重逻辑，重放后交付。
任务原文明确要求相同金额的不同记录分别计数；查询支持数据事实，不能替代这一需求依据。
六条中新流程只有这一条使用了额外查询，因此本轮不能单独证明主动取证的收益。

两条未交付原因分别为：

- 首参考已修正，但模型在 `finish` 引用最新重放中的具体检查 ID。
  初版接口只接受整轮重放 ID，连续拒绝了这些有效引用，导致无进展退出。
- 三方共同错误的负对照只修好 SQL 和首参考，独立核算仍错。
  该案例初始有三份错误程序，但预算最多修订两次；未全部修好受到明确的机制上限约束，
  不能直接归因为模型推理能力不足，也不能增加轮数后回填原成绩。

## 引用接口修复与离线回放

接口现接受最新重放 ID 或其中带版本的检查 ID；未知、过期和裸数据 ID 仍拒绝。
即使模型只引用一条检查，主机仍检查全部当前数据上的结果、未决假设和最终 SQL 执行。
修复没有增加模型轮次、放松一致性要求或修改任何题目答案。

2026-11-09 完成全部六条轨迹的原始响应回放，结果单独保存于
`reports/dispute-recovery-finish-replay/`。这不是新的真实模型实验：

- 正确交付由 4/6 变为 5/6；初始正确 SQL 被误拒的任务由 1/3 变为 0/3。
- 最终 SQL 仍为 6/6 正确，三份程序同时正确仍为 5/6；错误交付仍为 0/6。
- 全部六条的 SQL、首参考和独立核算最终文本均与原记录相同，共 18 份程序未变。
  新增交付仅来自首参考已修对的 `dispute-02`，不是重新生成了更好的程序。
- 17 个保存的模型回答按原顺序原样使用了 15 个：`dispute-01`、`dispute-02`
  各提前结束一轮，其余不变。没有消耗新增模型 tokens，不能据此宣称实测成本下降。
- 共同错误案例的一次只读查询重新执行，除运行耗时外，来源、标识和全部观察内容一致。
  每次动作前的任务、程序、版本、数据源绑定均与原记录相同。
- 三方共同错误的 `dispute-06` 仍未交付。没有放松全量检查或增加修订次数获得通过。

回放工具不创建 HTTP 客户端，不读取密钥或修改预算。修改后的提示词并未让模型重新作答，
因此这些结果只证明保存的回答在修复后的主机协议中如何运行，不能证明未来模型会做相同决定。
原实验目录全部 36 个文件在回放前后 SHA-256 均未改变。

本轮回放工具另修正了测试夹具遗漏创建父目录的问题，未改变运行时或评分逻辑。
已完成回放工具八项离线测试；最终全量回归结果记录于[续做记录](RESUME_DISPUTE_RECOVERY.md)。

三条初始正确 SQL 最终误改 0/3，但首轮仍有一条未交付。程序修复成功与任务交付成功
必须分别报告。新流程耗用 17 次请求、40,972 tokens；旧流程 15 次、32,208 tokens，
简单自审 6 次、10,842 tokens。当前没有速度或成本优势证据。

适合对外说明的范围是“六类受控开发场景、五个已见需求、每份程序 25 组固定输入，
支持三类程序定向修订及证据回放”。若引用 3/3 等结果，应一起说明这个开发样本范围。
不把 25 组输入扩写成 25 道任务，不宣称通用正确率 100%、零误判或性能提升百分比。

供复核的精简数字见[量化摘要](dispute-recovery-results/summary.json)，保留真实实验与
离线回放两个独立栏位；它不包含模型原始上下文或本机密钥配置。

## 审计与费用

独立审计不调用原评分汇总函数，逐格重新执行 SQL、参考与独立核算，重新计算交付、
修复和损伤数。18/18 格一致，0 项差异；冻结归档和 75 份源码的哈希在接口修复前
核对一致。后续代码已更改，重审原始实验需使用归档快照，不能要求当前代码哈希仍相同。

本轮共 38 次真实 HTTP 请求，事件 ID 无重复，已知输入 75,895 tokens、
输出 8,127 tokens，合计 84,022；未知用量为零。
按冻结单价输入每百万 0.8 元、输出每百万 2.7 元，增量估价为 0.0826589 元，
不是云账单核对金额。调用继续沿用原累计预算和账本，没有清空失败或退回历史预留。

## 下一步的唯一验证问题

先保留此版本，让下一轮回答：**在没有人工预先提供区分样本时，主动取证是否比直接自审
或相同流程关闭查询，更容易正确解决真实分歧，且不会误改正确 SQL？**

下一轮从已有公开题失败记录中按固定规则选一个小型开发子集，保留共同错误和正确样本。
相同原任务、原库权限、初始程序和预算下，比较简单自审、新流程不允许查询、新流程允许查询。
所有方法在相同来源交付；评分答案与真实期望结果不进入运行上下文。
先冻结选择规则和方法配置，再发请求。按任务而非每次样本执行统计交付率和配对差异，
同时记录错改、错误交付、未决、调用数及 tokens。

该子集只用于开发决策；有明确收益再进行未使用题目的确认。若仍无净收益，保留核验
与可追溯诊断能力，将复杂流程作为可选路径，不继续堆叠 Agent 或用新小样本覆盖旧失败。
