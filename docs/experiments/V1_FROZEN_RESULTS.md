## 本轮结论

新增机制在这批受控任务上体现了两项具体能力：区分 SQL 与参考程序中的单边错误，分别修复；遇到 SQL 和参考共同犯错时，通过独立核算发现分歧并阻止发布。

它仍未做到完整自动纠错：共同错误不能满足当前单目标修改的证据条件，需要澄清；两条本来能正确计算的任务耗尽复核轮次；一条自然任务的 SQL 正确，但首版参考擅自舍入仍未被运行时发现。因此“SQL 正确交付”和“三个计算程序全部正确”分别报告。

## 设计与分母

- 4 类公开开发需求：订单级平均、渠道筛选、订单去重、金额单位换算。
- 每类注入 4 种初始状态，共 16 条受控任务；仅首个 SQL、首版参考由评测器提供，后续核算、归因、修改均调用真实模型。
- 另有 4 条自然任务，SQL 与两份参考全部由模型生成。
- 每条任务评分使用源数据、6 组手工边界数据、24 组固定种子随机数据，共 31 组。评分数据与独立 Python 标准计算不进入模型上下文。
- 每条只运行一次，模型温度为 0；这不等于重复运行稳定性。20 条轨迹只涉及 4 类需求，31 组检查也不构成 31 个独立业务问题。

### 能力分项

- **单边 SQL 纠错：4/4。** 统计粒度、渠道范围、去重和单位换算错误均修复并交付；最终 SQL 与两份参考全部通过 31 组评分。
- **单边参考纠错：4/4。** 错误参考被替换，正确 SQL 得到保留；不能把参考程序默认当作标准答案。
- **正确 SQL 保护：8/8 保持语义正确，7/8 完成交付。** 没有把缺少结果算作保护成功；保护正确程序与完成任务是不同指标。
- **共同错误：4/4 观察到分歧并阻止发布，0/4 自动修复。** 独立核算得到正确结果，但原 SQL 和原参考共同错误。归因模型给出合法的 `candidate` 修改建议，运行时因缺少能支持该单目标修改的证据而转为待澄清。这不是模型主动选择澄清，也不是已经修复。
- **最终计算物质量：** SQL 候选 16/20、当前参考 15/20、独立核算 20/20 通过所有评分数据。这些包含未发布候选，不等于交付成功率，也不外推为模型总体准确率。

## 对照：哪些错误会被放行

对完全相同的 16 组初始产物做离线重放，初始 SQL 中 8 条正确、8 条错误：

| 检查阶段 | 接受的初始 SQL | 接受的错误 SQL | 接受的正确 SQL |
|---|---:|---:|---:|
| SQL 只读、合法且可执行 | 16 | 8 | 8 |
| SQL 与单份参考在初始数据上一致 | 8 | 4 | 4 |

单参考门禁放行的 4 条错误恰好是“SQL 与参考共同同错”组；完整 v1 发现了这些分歧，并将它们全部转为未交付，避免错误发布。单参考门禁拦下的另 4 条正确 SQL，则由完整 v1 替换错误参考后完成交付。

这说明增加核验与证据判断的工程价值，但不是移除 auditor 后的完整 Agent 消融实验。不能把两个门禁与完整系统的比例相减，称作“独立核算模块使准确率提升 X%”。

## 失败与局限

1. **`money_units__natural`：正确计算但未交付。** 首轮计划引用不匹配，经反馈纠正；随后两次探测使用不符合协议的时间格式，耗尽复核轮次。最终 SQL 与两个参考均通过 31 组数据，但状态是 `inconclusive`。
2. **`money_units__correct`：正确输入仍未交付。** 独立核算经历一次引用格式反馈；复核阶段生成了不符合整数量纲约束的测试数据，最终耗尽轮次。正确 SQL 没有被改错，但可用性仍受影响。
3. **`order_average__natural`：SQL 正确、参考仍有错误。** 首版参考擅自做两位小数舍入，在 31 组评分中仅通过 26 组；SQL 与独立核算均通过 31 组。运行时保留的测试没有触发该差异，说明有限反例搜索仍会漏检。
4. **共同错误只阻止发布。** 当前修改授权要求另一计算路径支持单目标修改；两份原始程序一起错误时，不能自动决定同时改两边。本轮没有把待澄清记成纠错成功。

未来最小改进优先考虑：减少探测数据格式错误对复核预算的消耗；增加能触发精度差异的探测覆盖。任何改动都应建立新的冻结实验，保留本轮结果，不覆盖成绩。双错误自动修复需要单独设计证据规则，不以放松发布条件替代。
