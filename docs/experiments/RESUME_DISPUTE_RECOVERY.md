## 2026-11-21 续做计划与源码参照

以下是拟开发和验收的内容。已有实验结果见 [六条轨迹的对照记录](DISPUTE_RECOVERY_RESULTS.md)。

1. **让用户提交问题并找回结果。** 以 ScholarSearch 的[任务提交](https://github.com/AlexYuanch/scholar_search/blob/02e27a4403526ec2981175b0c3d50e5810e1b097/src/App.tsx#L432)和[首次任务轮询](https://github.com/AlexYuanch/scholar_search/blob/02e27a4403526ec2981175b0c3d50e5810e1b097/src/App.tsx#L374)为全栈骨架。对照 Wren GenBI Classic 的[提问接口](https://github.com/Canner/WrenAI/blob/v1-final/wren-ai-service/src/web/v1/routers/ask.py)理解一次数据问答如何关联任务和结果。Classic 已冻结，本项目自行实现相应接口。FastAPI 提交后返回 run_id，后台执行现有 run_discovery，有可调查的分歧时显式调用 run_dispute_graph。页面用同一 ID 读取状态、结果与历史。验收时用支持范围内的新问题提交，刷新后能找回同一任务，两次读取不会重复发起模型调用。
2. **让用户看懂一次判断。** 参考 PaperFusion 的[运行证据报告](https://github.com/weijielin502-hub/paperfusion-agent/blob/bb2859c4e083ef0c7137375bc13014d4c9d7021d/paperfusion/report.py)。先用已保存的真实轨迹核对展示字段。页面列出原始需求、被质疑的程序版本、观察及来源、采用或拒绝的变更、最终执行结果。首个演示选“相同金额的不同记录分别计数”的真实轨迹，标出历史回放。随后用同一页面展示一次新任务。已确认的计数或退款口径随任务保存；原库、预览和合成数据要显示各自来源。
3. **检验主动查询的增益。** 对照简单自审、分歧流程关闭查询、同流程开启查询。冻结初始候选、原库和交付来源、模型、可访问数据和资源上限；只有第三组在分歧循环中启用主动查询动作。简单自审的对照应注明其可用的原库执行反馈。分别记录正确交付、错误交付、未交付、改坏原本正确的 SQL 和实际成本。六例开发集里的去重案例可说明机制，效果报告需另用留出需求。
4. **有需要时再迁移区分数据生成。** 按 [DPC 论文](https://aclanthology.org/2026.acl-long.313/) 及其[生成程序](https://github.com/HKUSTDial/DPC/blob/master/baseline/run_mdd_generation.py)检查失败样本。若多个任务反复因为原库缺少能区分解释的记录而未决，才增加提议样本的动作，复用已有约束检查与执行器。每个样本保存程序版本和实际输出；业务口径未定义时记录澄清问题。对照“仅查询”和“查询加样本”测额外收益。

首个里程碑是浏览器里贯通一条真实任务，能查到任务状态、可检查的 SQL 和最终处置。服务在模型请求前后分别中断的恢复测试，以及真正需要用户澄清的一次往返，作为可重复使用的工作台的后续验收。
