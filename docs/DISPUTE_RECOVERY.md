# 分歧处理原型

这是在现有三方核验之后使用的实验入口，尚未替换 `run_discovery` 的默认行为。
输入仍是原任务、同一数据样本、候选 SQL、首参考和独立核算。模型继续使用独立的
诊断上下文；变化是它现在能主动查询数据，并明确修订三份程序中的任意一份。

## 一次调查

1. 主机在相同有界数据上执行三份程序，记录不同输出或执行错误。
2. 诊断模型读取原始任务、当前程序和真实执行记录，选择查询、修订、结束或澄清。
3. 查询只能访问主机绑定的只读数据源。观察记录带数据范围和来源标识。
4. 修订指定 `candidate`、`reference` 或 `auditor`，同时提供需求引文、观察 ID
   和具体理由。主机不会自动把多数方的程序复制给少数方。
5. 新程序在全部保留样本上执行；无效修订保留记录而不替换旧版本。有效修订也只表示
   能执行及不违反调用方确认的样本，不表示语义已经正确。
6. 结束前重查当前三方结果，并实际执行最终 SQL。结果、版本及拒绝过的修改一并返回。

原库查询与小样本三方比较分开记录。若使用 `query_source` 指定真实原库，最终交付
结果来自该原库；参考与独立核算仍只在相同的有界样本上比较，不能声称它们计算了原库全量数据。

- [模型动作与提示词](../dataverify/agent/dispute_model.py)
- [LangGraph 调查流程](../dataverify/agent/dispute_graph.py)
- [主机绑定的只读 SQL 工具](../dataverify/verification/sql_tools.py)

`run_dispute_graph` 接收已生成的三份程序及调用方提供的模型客户端。它不隐式创建
API 客户端、不读取评分答案、不修改任务定义，也不负责重新生成整个项目。
旧流程的未决结果可由调用方取出 `candidate.sql`、`plan` 和 `audit_plan`，
连同原任务及保留的 `fixtures` 显式传入此入口。

默认每次调查最多 4 次模型动作、2 次额外查询、2 次程序修订；连续无进展也会退出。
无效动作仍消耗模型调用预算。缓存查询不重复执行 SQL，但不会获得无限免费轮次。
独立实验器先持久化调用标记，付费中断后不自动重跑同一格。[工作台](WORKBENCH.md)在同一分歧图外增加了持久化动作日志。服务重启后按已记录的回复恢复任务。如果请求已经发出、模型回复尚未写入日志，任务会停止并说明原因，以免重复付费。

## 结果的含义

- `reviewed`：当前有限检查通过，最终 SQL 实际执行完成；不是语义正确性证明。
- `needs_clarification`：模型提出了具体、尚缺失的业务定义。
- `inconclusive`：预算、工具、格式或未解决分歧等原因使本轮未完成；具体原因保留。
- 修订记录的 `accepted`：主机采用了该可执行版本，不等于“修复正确”。

三方可能共同误解需求；这一机制不会把“大家一致”升级为真值。真实效果应通过
独立评分统计修复、损坏、正确结果被拒绝及错误交付，不能只展示阻断数或通过数。

## 开发验证

离线验证使用编写的模型响应，只验证状态机、版本、工具与边界。
真实模型开发对照由 [实验入口](../tools/evaluate_dispute_recovery.py) 执行，
比较简单自审、旧三方流程和本原型；默认仅准备，`--execute` 才发出请求。
所有付费请求复用已有累计授权及预算账本。
